# Мост между NABVE1 и внешним ботом (например, Telegram)

NABVE1 не содержит клиента ни для одного мессенджера — эта функциональность
(логин, приём/отправка сообщений) намеренно вынесена в отдельный проект,
который вы запускаете отдельным процессом. `modules/messaging` внутри
NABVE1 — это только очередь входящих/исходящих + голосовой интерфейс
(«следи за», «ответь», «отложи»). Обмен между NABVE1 и вашим ботом идёт
через HTTP API самого NABVE1 (тот же сервер, что отдаёт `/api/*` для
фронтенда), а не напрямую через SQLite — так бот не завязан на внутреннюю
схему БД и бизнес-логику (нормализация identifier, слияние сообщений от
одного контакта и т.д. — она вся уже сделана на стороне NABVE1).

Базовый URL: `http://127.0.0.1:{ASSISTANT_PORT}` (по умолчанию порт 8756,
см. `core/config.py`). Каждый запрос должен нести тот же токен, что и любой
другой `/api/*` вызов — либо заголовком `X-Assistant-Token: <token>`, либо
query-параметром `?token=<token>`. Токен лежит в `data/api_token.txt`
(создаётся автоматически при первом запуске NABVE1).

## 1. Входящее сообщение (бот → NABVE1)

```
POST /api/messaging/incoming
{
  "source": "telegram",
  "sender_identifier": "@ira",   // как отдаёт ваш клиент — @username или id
  "sender_label": "Ира",         // отображаемое имя, для голосового объявления
  "text": "привет"
}
```

Ответ:

```
{ "recorded": true, "message_id": 42 }
```

`recorded: false` — контакт не в списке отслеживаемых (`messaging_watch_contact`
ещё не вызывался голосом/через API для этого identifier с `source: "telegram"`)
— NABVE1 намеренно не хранит вообще ничего от контактов, за которыми не
попросили следить. Это не ошибка, просто no-op.

Вызывайте этот эндпоинт на каждое новое входящее сообщение, которое видит
ваш бот, независимо от того, отслеживается ли контакт — фильтрация уже
встроена на стороне NABVE1.

## 2. Исходящие сообщения (NABVE1 → бот)

Опрашивайте очередь на отправку (poll, не push):

```
GET /api/messaging/outbound/pending
```

Ответ — список ожидающих отправки:

```
[
  {
    "id": 7,
    "source": "telegram",
    "recipient_identifier": "ira",   // уже нормализован: без @, в нижнем регистре
    "text": "привет!",
    "created_at": "2026-08-13T18:20:00"
  }
]
```

После попытки отправки — обязательно подтвердите результат, иначе
сообщение так и останется в `pending` и будет возвращаться при каждом опросе:

```
POST /api/messaging/outbound/{id}/ack
{ "status": "sent" }     // или "failed"
```

Разумный интервал опроса — раз в несколько секунд (это личный ассистент
одного пользователя, не production-очередь, нагрузка тривиальна).

## Что уже сделано на стороне NABVE1, и о чём боту думать не нужно

- Нормализация identifier (регистр, ведущий `@`) — уже применена к
  `recipient_identifier` в исходящих и при матчинге входящих.
- Слияние нескольких сообщений от одного контакта в одну «ожидающую»
  запись, снятие со snooze при новом сообщении — вся эта логика в
  `modules/messaging/service_layer.py`, дублировать её в боте не нужно.
- Авторизация — тот же токен, что использует Electron-фронтенд и LAN/QR
  тонкий клиент.

## Что осознанно не сделано

Нет push-уведомлений от NABVE1 к боту о новых исходящих — только polling.
Нет retry/backoff политики на стороне NABVE1 при `status: "failed"` —
запись просто помечается `failed` и остаётся в истории; повторная отправка,
если нужна, — забота бота (перезапросить `pending` он не может, т.к. row
уже не `pending` — при необходимости добавьте retry-логику на своей
стороне до вызова `ack`).
